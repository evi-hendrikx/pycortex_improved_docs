# Pycortex Conceptual Documentation Improvement — Design Doc for Claude Code

## Background / problem statement

The pycortex documentation site (https://gallantlab.org/pycortex/index.html,
source in `docs/`) is structured
as a loose set of reference pages (Installation, Surface Segmentation and
Flattening, Surface Database, Alignments, Surface-defined ROIs, Transform
formats, Colormaps, Example Gallery, API Reference). Individually these
pages describe *how* to invoke specific pieces of pycortex, but:

- There is **no roadmap / orientation page**: a new user landing on the site
  has no page that says "here is the mental model of what pycortex does and
  in what order you'll use its pieces."
- There is **little to no conceptual "why"**: pages jump straight into
  file formats and CLI-style instructions (e.g. `database.html` opens with
  filestore directory layout) without first explaining the underlying
  problem pycortex solves (why surface visualization at all? why not just
  look at volume slices? what is a flatmap and why would you cut/relax a
  cortical mesh?).
- Terminology is used before it's defined (e.g. "fiducial surface", "xfm",
  "filestore", "flatmap", "CTM") — a returning lab member knows these, a new
  user does not. Maybe make a dictionary?
- The pieces (surfaces, transforms, database, masks, flatmaps, WebGL
  viewer) are documented in **isolation**, so it's hard to see how a user's
  data actually flows through the system end-to-end: FreeSurfer output →
  pycortex surface import → alignment/transform → functional data + mask →
  Volume/Vertex object → flatmap or WebGL view.
- The **actual conceptual grounding already exists** — it's just trapped in
  the 2015 Frontiers in Neuroinformatics paper (Gao, Huth, Lescroart &
  Gallant, 2015, "Pycortex: an interactive surface visualizer for fMRI",
  doi: 10.3389/fninf.2015.00023) and never made it into the docs site. The
  paper explains, in accessible terms: why volume-slice and standard surface
  visualization are inadequate, what "pixel-wise sampling" is and why it
  beats interpolation-based approaches, how the folded → inflated → flattened
  surface continuum works and why each stage matters, and why an
  interactive/WebGL-based tool matters for exploring high-dimensional
  functional data. This paper is the single best source of "why" content
  and should be mined directly (with proper paraphrasing/attribution, not
  copied) as the intellectual backbone for the new conceptual pages.

## Goal

Restructure and rewrite the pycortex documentation (the **narrative /
conceptual** pages, not the auto-generated API reference — that's a
separate project) so that:

1. A new user can read one "start here" page and come away with an accurate
   mental model of what pycortex is, what problem it solves, and what the
   major moving pieces are (surfaces, transforms, database/filestore,
   Volume/Vertex data objects, flatmaps, the WebGL viewer) and how they
   relate to each other.
2. Each existing conceptual page (segmentation/flattening, database,
   alignments, ROIs, transforms, colormaps) opens with a short "why does
   this exist / what problem does it solve" explanation *before* diving
   into file formats and commands, grounded in the actual computational
   and neuroscientific reasoning (drawn from the paper and the source code
   itself), not just restated instructions.
3. There's a clear, linear **roadmap / workflow diagram** a new user can
   follow: "I have FreeSurfer output and fMRI data, what do I do, in what
   order, and why does each step exist?"

## Constraints — read carefully

- **This is a documentation-only project.** Do not modify any `.py` source
  file or docstring, and do not change any actual program behavior.
- You **may** edit, restructure, and rewrite the existing narrative `.rst`
  files under `docs/` (e.g. `database.rst`, `align.rst`, `rois.rst`,
  `transforms.rst`, `colormaps.rst`, `segmentation_guide.rst`, `index.rst`,
  `install.rst`) since improving these *is* the task — unlike the previous
  API-example task, these are prose/conceptual docs, not auto-generated
  from docstrings, so editing them directly is the correct approach here.
  Confirm this understanding is right by checking whether these are indeed
  hand-written `.rst`/`.md` files in `docs/` (not autosummary-generated)
  before editing — if any turn out to be autogenerated, treat them as
  read-only source and write your improved version alongside instead, and
  flag the discrepancy.
- Do **not** delete existing content outright without preserving its
  substance somewhere — restructure/rewrite in place, and where you cut
  something, make sure the information isn't simply lost (fold it into the
  new structure or an appendix).
- **Do not fabricate technical claims.** Ground every conceptual
  explanation in one of: the Frontiers paper, the pycortex source code
  itself, or the existing docs. If you're not sure why something is
  designed a certain way, say so explicitly (e.g. as an inline TODO/comment
  or in the summary notes) rather than inventing a plausible-sounding
  rationale.
- **Respect copyright on the paper.** Do not reproduce paragraphs or figure
  captions from the Frontiers paper verbatim. Paraphrase concepts in your
  own words; cite the paper (title, authors, year, DOI) as a reference for
  readers who want the full technical detail, rather than lifting text.
  Figures from the paper should not be reproduced as images unless you
  confirm they are separately available under a compatible license (they
  are CC-BY per Frontiers' standard license — verify this before reusing
  any figure, and always attribute).
- Keep all code snippets/examples in the docs **accurate and runnable**
  against current pycortex — if you add or keep an example, verify it
  against current source (function names, signatures) rather than assuming
  older docs were correct.

## Source material to use

1. **The paper**: Gao JS, Huth AG, Lescroart MD, Gallant JL (2015).
   "Pycortex: an interactive surface visualizer for fMRI." Front.
   Neuroinform. 9:23. doi: 10.3389/fninf.2015.00023. Full text:
   https://www.frontiersin.org/journals/neuroinformatics/articles/10.3389/fninf.2015.00023/full
   Use this for: the motivation (why surface viz over slices/standard
   surface tools), the pixel-wise sampling explanation, the
   folded/inflated/flattened surface concept, the WebGL/static-view
   rationale, ROI overlay rationale.
2. **The existing docs** in the repo pycortex_improved_docs/docs
3. **The pycortex source code**, especially module-level docstrings in
   `cortex/align.py`, `cortex/database.py`, `cortex/dataset/`,
   `cortex/quickflat/`, `cortex/webgl/`, `cortex/xfm.py`, `cortex/utils.py`
   — these often contain useful conceptual context that never made it into
   the prose docs.
4. **The example gallery** (`docs/auto_examples` / the built Example
   Gallery page) — real working code that shows the intended end-to-end
   workflow; use this to sanity-check the roadmap you write is actually
   accurate to how the tool is used in practice.
5. **CONTRIBUTING/README/CHANGELOG** in the repo, for terminology and any
   stated design philosophy.

## Deliverables

### 1. New landing / "start here" page: `docs/overview.rst` (or rework `docs/index.rst`)

A conceptual on-ramp, roughly in this shape (adjust as the material
warrants — this is a starting outline, not a rigid template):

- **What problem does pycortex solve?** (2–4 paragraphs) Why volume-slice
  viewing and naive surface rendering are inadequate for understanding
  fMRI activity spread across folded cortex; why pixel-wise sampling from
  volume onto a surface mesh is a meaningfully different/better approach
  than interpolation-based approaches; why an interactive,
  folded ⟷ inflated ⟷ flattened continuum matters for interpreting data.
  (Paraphrased from the paper's Introduction/motivation, cited.)
- **The core mental model**: a short explanation + a diagram (Mermaid or
  ASCII, see "Diagrams" below) of the main objects and how data flows
  between them, e.g.:
  `FreeSurfer anatomical surfaces → pycortex surface database (per-subject
  filestore) → alignment/transform (functional-to-anatomical) → mask →
  Volume/Vertex data object → flatmap image (quickflat) and/or interactive
  WebGL viewer`
- **"Which page do I need?"** — a short guide mapping user intent to doc
  page, e.g. "I just got FreeSurfer output and want to see it in pycortex"
  → Surface Segmentation and Flattening + Surface Database; "I have a
  functional volume I want to align" → Alignments; "I want to draw/use
  ROIs" → Surface-defined ROIs; "I want a static image" → quickflat +
  Example Gallery; "I want an interactive 3D view" → webgl.
- **Core vocabulary** — a short glossary of terms used everywhere in the
  docs without definition (subject, xfmname, filestore, fiducial surface,
  flatmap, mask, CTM, Volume vs Vertex, pixel-wise sampling). One or two
  sentences each; link to the fuller explanation on whichever page owns
  that concept.
- **A minimal end-to-end "hello world"** — the shortest path from "I have
  no data" to seeing something in pycortex (the built-in demo subject),
  so a new user gets a working result in their first five minutes, before
  reading anything else.

### 2. Rework each existing conceptual page to open with "why"

For each of: `segmentation_guide.rst`, `database.rst`, `align.rst`,
`rois.rst`, `transforms.rst`, `colormaps.rst` (confirm exact filenames in
`docs/` — names above are inferred from the rendered URLs and may differ
slightly):

- Add a short **"Why this exists" / "The problem this solves"** section at
  the top, before the technical/file-format details, e.g.:
  - *Alignments*: why functional and anatomical data start out
    misregistered, what an affine transform is fixing, why manual
    (FreeView) vs automatic (BBR) alignment exist as separate options and
    when you'd use each.
  - *Surface Database*: why pycortex needs its own filestore at all (vs.
    just pointing at FreeSurfer's `SUBJECTS_DIR` directly), what problem
    the fiducial/flat/inflated multi-surface requirement solves.
  - *Transform formats*: why transforms are stored the way they are
    (coord vs magnet space), what breaks if you get this wrong.
  - *Surface-defined ROIs*: why ROIs are stored as SVG overlays on the
    flatmap rather than as volumetric labels, what that buys you.
  - *Colormaps*: why 1D vs 2D colormaps exist, when you'd need a 2D
    colormap (this connects to `VolumeRGB`/`Volume2D` from the dataset
    API — cross-link).
- Keep all existing correct technical/procedural content — restructure and
  clarify, don't strip it out. Fix anything factually stale or contradicted
  by current source while you're in there, but the focus of this task is
  conceptual framing, not an exhaustive technical audit (that's covered by
  the sibling API-docs project).
- Tighten prose throughout: short paragraphs, define terms on first use,
  avoid unexplained jargon, add cross-links to the glossary/overview page
  and to relevant API reference pages.

### 3. Add a roadmap diagram

Create at least one diagram (Mermaid, rendered via `sphinx.ext.graphviz`,
or plain ASCII if Sphinx can't render Mermaid in this repo's setup — check
`docs/conf.py` for what's already configured, e.g. `sphinx_gallery`,
`numpydoc`, and add a diagram extension only if one isn't already
available and it's low-friction to add) showing the full pipeline:

```
FreeSurfer recon-all
        │
        ▼
cortex.freesurfer.import_subj  ──►  pycortex surface database (filestore)
        │                                    (fiducial, flat, inflated surfaces)
        ▼
cortex.align (manual / automatic)  ──►  functional-to-anatomical transform (xfm)
        │
        ▼
functional data (volume) + mask  ──►  cortex.Volume / cortex.Vertex
        │
        ├──► cortex.quickflat.make_figure / make_png  ──►  static flatmap image
        └──► cortex.webgl.show / make_static          ──►  interactive 3D/flat viewer
```
Verify this pipeline against the actual example gallery and source before
publishing it — the above is a first-draft sketch for orientation, not a
verified final diagram. Correct anything inaccurate.

### 4. Glossary

A single glossary page or section (can live on the overview page, or as
`docs/glossary.rst` linked from it) defining: subject, xfmname, filestore,
fiducial surface, flat surface, inflated surface, flatmap, mask, CTM
(OpenCTM mesh format), pixel-wise sampling, Volume vs Vertex, Dataset,
ROI overlay (SVG), dropout. Extend the list if other undefined jargon
turns up while reworking the pages above.

### 5. Suggestions for examples

Write an .md file with suggestions for examples that can elegantly demonstrate what is described in the text of each section. Also, if an example that is currently given is not correct or not complete enough, make suggestions for changes.

## Process for Claude Code

1. Check out / read `docs/conf.py` and the `docs/` directory tree to see
   exactly which `.rst` (or `.md`, if using MyST) files back each rendered
   page, and confirm none of them are autosummary/autodoc-generated (they
   should be hand-written prose — verify before editing).
2. Read the Frontiers paper (fetch the full text, don't rely on
   abstract/snippets) and take structured notes on the motivating
   arguments and technical concepts you'll paraphrase — keep these notes
   in a scratch file so citations stay accurate as you write.
3. Read each existing conceptual doc page's source and the relevant
   source-code modules it documents.
4. Draft `docs/overview.rst` (or the reworked `index.rst`) first, since it
   sets the vocabulary and structure the other pages should link back to.
5. Then work page-by-page through the existing conceptual docs, adding the
   "why" framing and tightening prose, preserving correct existing content.
6. Add the roadmap diagram and glossary.
7. Do a final pass: click through the intended reading order as a new user
   would, check all cross-links resolve, and confirm the "hello world"
   example actually runs against current pycortex.
8. Try building the docs locally (`pip install sphinx_gallery numpydoc`,
   `cd docs && make html`) to confirm nothing is broken, and note in your
   summary if you weren't able to build (e.g. missing system dependencies)
   rather than silently skipping this check.
